# Stage62：原官方UFG短形状源训练充分性续训

## 为什么要做

精度目标要求超过充分训练的官方有效UFG，不能只超过人为截短的对照。Stage59中12→12最佳9000、在10000上限结束，尚未满足原八轮无0.1%源改善的早停；48→24最佳3500、5500按早停退出。此前所有有限预算结果保留，不把10000上限称作收敛。本阶段只延长未满足早停的短分支，不改变结构、宽度128、31角色和相同实际历史节点/全节点标签资格，不读取目标标签或成绩。

## 固定改变与精确接续

仅将短形状最大更新从10000增加到20000，其余原Adam1e-3、batch64、每250验证、至少2000、独立0.1%参考与连续8轮早停全部不变。不重新初始化模型或优化器，不改损失/数据/变量/归一化/种子/查询顺序。保留原last、best、全部验证及曲线，创建新快照/输出stage62-official-ufg-source-adequacy-v1，原目录只读。

读取原最终last.pt的模型、Adam复杂数状态、梯度、Python/NumPy/Torch RNG、游标、选模及活动时间，严格验证原来源binding和最后完整10000验证。新副本只改变事务binding、completed结束标记及移除上限停止原因；对所有数值状态计算规范SHA，迁移前后必须完全一致。此为明确改变上限后的源续训，不冒称原预算未改变。使用原UFG环境保存迁移状态，避免跨NumPy/PyTorch序列化版本变化。后续资源/合作暂停仍使用原部分梯度和优化器恢复，不重新计已完成的验证/更新。

48→24原源最佳原样引用，不再训练。两分支均满足原固定源早停标准后才记录“源训练充分性标准满足”，不声称数学全局最优；若新20000上限仍先到达，明确记录未满足充分性标准，不靠目标成绩再挑旧弱权重。

## 验收与成本

B静态，C禁CUDA、OMP/MKL各2线程，检查binding/完成标记以外状态逐位一致、下一次优化器更新及RNG一致、错误来源与不完整事务拒绝、复数状态和部分梯度SHA、原UFG31节点/复杂优化器恢复。另用真实原UFG10000更新状态和原下一批64查询，在两份内存副本比较下一更新，容差CPU1e-6；仅QA，不改变原模型，不计为正式新增更新。

纯CPU，无新GPU/ChatTime加载、无目标预测入口。原8091.692秒UFG CPU成本只作为继承记录，额外CPU驻留单独计；原GPU祖先与并行Stage60/61账本不清零、不重复相加。新模型/配置/来源SHA和锁定目录单独交付。Stage60旧源快照中的UFG副本不编辑；未来部署组合必须明确绑定新的充分性对照，不暗中改写既有报告。
